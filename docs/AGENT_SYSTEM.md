# Agent workforce — implemented boundary

The API can seed one per-token Head Manager and ten distinct role identities: Android, Web, Game, UI/UX, Backend, Database, Security, QA, Research, and Documentation. Their role IDs, prompts, provider/model settings, specialties, temperature/context preferences, status, priority, memory toggle, bounded duration, and permission metadata persist in the database. Credentials are attached to owner-scoped provider connections, not agent rows.

`POST /api/v1/tasks/{id}/execute` performs real provider calls through the configured provider router. The Manager returns a JSON plan; the API accepts only 1–5 unique known worker identities, persists assignments, calls the workers serially, stores reports, and requests final Manager synthesis. Parse/provider errors mark the task failed; no fabricated answer is stored. The plan cannot invoke tools. A single API request currently runs the whole operation; no queue process, scheduler, parallel delegation, lease, crash resume, cancellation, or automatic retry loop exists. Explicit user retry is bounded by `max_attempts`.

Agent memory is a small owner-scoped notes table, not vector search. With memory enabled, an agent receives up to six high-importance agent/headquarters notes as quoted context; project notes are stored but not yet attached to tasks. Agent-to-agent messages are persisted and owner-scoped. Tool permissions default empty and are descriptive only; shell and external action tools do not exist.

Use `/api/v1/agents/seed` idempotently. Configure and test each provider connection, then edit each agent's exact provider and discovered model ID. Repeated identities remain independent even if provider/model values are shared. `docs/ARCHITECTURE.md` lists the deployment constraints; do not represent this API-triggered serial executor as a durable workflow service.
