# Security posture

NOVA remains an early-stage, not production-ready application. Do not expose the development server or send sensitive production data until you deploy TLS, shared gateway rate limits, database migration/backup controls, secret-manager storage/rotation, and a durable worker design.

## Added workforce controls

- API keys are hashed at rest and scopes are enforced on every user API. Agents, tasks, memories, provider connections, usage and events are filtered by `owner_key_id`; cross-owner IDs return not found.
- Ordinary app-client endpoints reject upstream provider API keys. Upstream keys should be injected into backend runtime secrets or stored in the external gateway. The app may submit only a restricted compatible-gateway access token over HTTPS; stored connection tokens use authenticated Fernet encryption with the separate `NOVA_CREDENTIAL_ENCRYPTION_KEY`, are never returned in API views, and are never stored in Android preferences. To rotate encryption, set the new primary key plus old key in `NOVA_CREDENTIAL_ENCRYPTION_KEY_PREVIOUS`, call admin-only `POST /api/v1/admin/credentials/rotate`, verify counts, then remove the previous key after backup. Revoke gateway tokens at the gateway when disconnecting.
- Built-in adapters use fixed provider API endpoints. User-configured gateway endpoints are accepted only for `claude_gateway`, generic `openai_compatible`, or `anthropic_compatible`, and must be an HTTPS `https://<allow-listed-host>/v1` URL where the exact hostname is listed in backend `NOVA_GATEWAY_ALLOWED_HOSTS`. The adapter rejects URL credentials, query/fragment strings, non-HTTPS, unlisted hosts, non-default ports, and other paths. This operator allow-list is an SSRF boundary, not arbitrary URL access. Gateway tokens are encrypted and model IDs are obtained through owner-authenticated model discovery.
- Router retries/fallback are finite. 402 billing errors stop. Provider bodies are not reflected in error responses. Per-connection and owner request budgets are checked before calls; provider-specific rate and spend controls remain authoritative.
- Task plans are constrained to known role IDs, a maximum of five unique assignments, and persisted assignment status. Worker tools default off and require exact per-agent permission; the only implemented tools are bounded arithmetic, text counts, and owner/agent-scoped note search. Requests are validated server-side and denied calls are audited. There is no shell, filesystem, browser, arbitrary network, or external-action tool. Provider output and memory are untrusted text; no instruction from them is executed as a host action.
- The admin infrastructure API requires `NOVA_ADMIN_TOKEN`; it is not accessible with ordinary scoped API credentials.

## Remaining production gaps

Task execution can run in the API or the separate database-backed polling worker. PostgreSQL task capacity checks use advisory locks and task claims use conditional database updates; a live multi-replica stress test is not available. Plan changes can repeat work. PostgreSQL event fan-out requires migration 0008; SQLite and each instance's socket registry remain local. Stream disconnects close upstream and report cancellation/interruption but do not resume the same provider generation. There is no approval workflow, user-configurable retention/deletion for all task audit data, or production deployment. Request rate limiting is process-local (now scoped by client and a one-way bearer hash), and does not replace shared edge controls. Review `docs/ARCHITECTURE.md` before operating this branch.

Never commit provider keys, API tokens, admin secrets, encryption keys, user conversations, local DB files, or backups. Use synthetic test secrets and mocked provider HTTP responses.
